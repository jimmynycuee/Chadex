# Chadex 0.4.1

Chadex 0.4.1 closes the automatable portion of the Windows W5 release-readiness track and simplifies instruction ownership before release. Chadex now separates app-managed **Global Instructions** from repository-native `AGENTS.md` hierarchy while preserving the existing safety/authority envelope. The Windows application remains an unsigned CI validation candidate; the public release workflow continues to publish only the macOS Apple Silicon DMG unless a later release task explicitly changes that policy.

## Changes

- Replaced the editable project-`AGENTS.md` surface with **Chadex Global Instructions**, an app-owned preference shared across all Chadex projects. It is available even when no project is selected or connected.
- Global Instructions are stored outside repositories as `global-instructions.md` in Chadex app data (`~/Library/Application Support/Chadex/` on macOS; Tauri app-local-data on Windows). Both platforms enforce UTF-8, an 8 KiB bound and regular non-symlink storage; the runtime receives only this Chadex-owned path.
- Repository instructions remain native repository files. Chadex still honors the registered project root and target-scoped nested `AGENTS.md` hierarchy, but no longer inherits an ambient ancestor `AGENTS.md` outside the registered project root. In particular, a parent such as `~/Documents/ChatGPT/AGENTS.md` is never treated as Chadex Global Instructions.
- Defined the behavioral precedence as **current user instruction → most-specific nested repository AGENTS.md → repository-root AGENTS.md → Chadex Global Instructions → Chadex built-in baseline**. System/platform safety, authority, approval and sensitive-content constraints remain a non-overridable outer envelope; blank Global Instructions are a safe no-op.
- Agent Settings now presents Global Instructions as editable app state and Repository Instructions as read-only repository state, removing the misleading repo-`AGENTS.md` create/edit affordance.
- Reworked the macOS **Computer Use** settings hierarchy around a single Control mode section, current approval request, and Safety section. Stopped state now hides all other controls and exposes only **Resume Computer Use**, matching the actual kill-switch state.
- Added a real persistent **Always allow** Computer Use mode. It survives future tunnel sessions, while **Allow this session** remains temporary. Stop remains authoritative across reconnects until the user explicitly resumes. Existing hard blocks for secure/protected UI surfaces remain independent of this preference.
- Advanced Chadex-owned macOS/runtime/Windows product metadata to `0.4.1`; the Windows synthetic installer-migration fixture now models `0.4.0 → 0.4.1`.
- Added a native Windows historical-source upgrade gate. CI builds the exact public `v0.4.0` tag in an isolated worktree, installs that real older binary/resource set, then upgrades it to the current tested candidate and rechecks resource hashes, preferences/project-data preservation, relaunch, reinstall, uninstall, process ownership and cleanup.
- Kept the existing synthetic-metadata upgrade test as a separate fast invariant instead of treating it as evidence of historical source compatibility.
- Added an isolated NSIS default self-copy uninstall stage. The existing `_?=` in-place uninstall remains useful for exact post-exit file assertions, while the new stage exercises the normal NSIS uninstaller behavior and still requires verified registry removal, zero residual owned processes and zero forced cleanup.
- Refined the sanitized W5 report so historical source identity and external acceptance boundaries are explicit without exposing local paths, credentials or raw backend errors.

## Validation

The v0.4.1 release candidate must pass the normal source/history/macOS package gates, Windows W2/W3 regression gates, W5 source-integrity gate, the synthetic installed lifecycle, the historical `v0.4.0 → v0.4.1` installed lifecycle and the default NSIS self-copy uninstall stage. Instruction-specific validation additionally covers an empty/no-`AGENTS.md` project, cross-project Global Instructions storage, offline editing, ambient-ancestor isolation, Global + repository precedence, target-scoped nested rules, and native macOS/Windows storage contracts. Exact final CI run IDs and sanitized counts are recorded in the W5 handoff after the candidate HEAD is validated.

Portable W5 regressions cover candidate/historical manifest validation, hash/path fencing, sanitized reporting, CDP policy ownership/cleanup, process identity rules and both controlled/default uninstaller command contracts. Portable Python and Node regressions also run locally through explicit interpreter paths; native Windows Tauri/Rust packaging and installed lifecycle behavior remain CI evidence.

## Remaining external acceptance

W5 automated release engineering does not substitute for evidence that requires a real user environment or a distribution decision. The following remain outside the automated closeout unless separately validated: physical Windows 11 interaction, Windows ARM64 hardware/builds, native picker/Explorer/tray/launch-at-login/notification behavior, a credentialed ChatGPT tunnel workflow, Authenticode signing and SmartScreen reputation, a host genuinely missing WebView2, interactive installer choices, Credential Manager deletion policy on uninstall, and a production Windows updater/delivery policy.

## Distribution boundary

`.github/workflows/release.yml` remains the free macOS distribution path. It does not publish the Windows W5 candidate. A passing Windows CI candidate is therefore release-engineering evidence, not a signed/public Windows release. Publishing Windows assets, enabling a Windows updater or changing the signing policy requires a separate explicit release decision.
