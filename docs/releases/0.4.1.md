# Chadex 0.4.1

Chadex 0.4.1 closes the automatable portion of the Windows W5 release-readiness track without changing the public distribution boundary. The Windows application remains an unsigned CI validation candidate; the public release workflow continues to publish only the macOS Apple Silicon DMG unless a later release task explicitly changes that policy.

## Changes

- Advanced Chadex-owned macOS/runtime/Windows product metadata to `0.4.1`; the Windows synthetic installer-migration fixture now models `0.4.0 → 0.4.1`.
- Added a native Windows historical-source upgrade gate. CI builds the exact public `v0.4.0` tag in an isolated worktree, installs that real older binary/resource set, then upgrades it to the current tested candidate and rechecks resource hashes, preferences/project-data preservation, relaunch, reinstall, uninstall, process ownership and cleanup.
- Kept the existing synthetic-metadata upgrade test as a separate fast invariant instead of treating it as evidence of historical source compatibility.
- Added an isolated NSIS default self-copy uninstall stage. The existing `_?=` in-place uninstall remains useful for exact post-exit file assertions, while the new stage exercises the normal NSIS uninstaller behavior and still requires verified registry removal, zero residual owned processes and zero forced cleanup.
- Refined the sanitized W5 report so historical source identity and external acceptance boundaries are explicit without exposing local paths, credentials or raw backend errors.

## Validation

The v0.4.1 release candidate must pass the normal source/history/macOS package gates, Windows W2/W3 regression gates, W5 source-integrity gate, the synthetic installed lifecycle, the historical `v0.4.0 → v0.4.1` installed lifecycle and the default NSIS self-copy uninstall stage. Exact final CI run IDs and sanitized counts are recorded in the W5 handoff after the candidate HEAD is validated.

Portable W5 regressions cover candidate/historical manifest validation, hash/path fencing, sanitized reporting, CDP policy ownership/cleanup, process identity rules and both controlled/default uninstaller command contracts. Portable Python and Node regressions also run locally through explicit interpreter paths; native Windows Tauri/Rust packaging and installed lifecycle behavior remain CI evidence.

## Remaining external acceptance

W5 automated release engineering does not substitute for evidence that requires a real user environment or a distribution decision. The following remain outside the automated closeout unless separately validated: physical Windows 11 interaction, Windows ARM64 hardware/builds, native picker/Explorer/tray/launch-at-login/notification behavior, a credentialed ChatGPT tunnel workflow, Authenticode signing and SmartScreen reputation, a host genuinely missing WebView2, interactive installer choices, Credential Manager deletion policy on uninstall, and a production Windows updater/delivery policy.

## Distribution boundary

`.github/workflows/release.yml` remains the free macOS distribution path. It does not publish the Windows W5 candidate. A passing Windows CI candidate is therefore release-engineering evidence, not a signed/public Windows release. Publishing Windows assets, enabling a Windows updater or changing the signing policy requires a separate explicit release decision.
