# Chadex 0.5.0

Chadex 0.5.0 makes Skills a first-class, manageable part of the app and speeds up launch and connection. It adds read-only connection of external Skill folders, a standalone Skills page on macOS (with Windows parity), simpler ZIP import and removal, and a local admin token that keeps Skill/Memory management off the tunnel. The local runtime is now prepared in the background at launch. Public distribution remains the macOS Apple Silicon DMG; the Windows application remains an unsigned CI validation candidate.

## Changes

### External Skill sources

- Added **External Skill sources**: connect an Agents, Claude Code or Codex Skills folder to Chadex. Sources are configured at the Runner level, so they apply across projects instead of being copied into each one.
- External Skill scripts are not executable by default. Each external source must be enabled for script execution individually.

### Skills page and management

- Added a standalone **Skills** page on macOS with a compact list, search and filters, an enable switch per Skill, and a clear **Remove** action for installed Skills (with confirmation). The page content is centered in a readable column.
- Windows reaches Skills UI parity: compact Skills page with sources first, search and filters, SKILL.md preview, a remote-runtime notice and an aligned top bar.
- Skill ZIPs can be imported from any location. The ZIP is staged under `.chadex/skill-imports/` in the project and deleted afterwards; `.gitignore` is only touched in git checkouts, and staging runs off the main actor.
- A ZIP whose contents sit inside a single top-level folder is flattened automatically.
- Install and import failures now report the concrete cause instead of a generic error, including replay-capacity errors and per-project effects.
- Removing a Skill is shared by the whole local runtime, so every project loses it together; the confirmation says so.

### Local admin token and tunnel ingress

- Added a local admin token (`chadex-desktop-admin`) used by Chadex itself for Skill and Project Memory management, separate from the token ChatGPT uses.
- The tunnel ingress refuses Skill and Memory management tools, and fails closed on MCP bodies it cannot parse.
- Skill-root path handling was hardened on Windows (junction and alias bypasses).

### Launch and connection speed

- The local runtime is prepared in the background at launch (on by default and can be turned off in settings). macOS and Windows both prewarm, with quiet failure handling, a bounded cancel wait, no relaunch after quit, and safe behavior at quit.
- When the prewarmed runtime is already running, Chadex realigns it to the selected project without touching the tunnel.
- An unstarted runtime is shown as stopped, and Connect gives faster feedback.
- Lifecycle traces now cover prewarm, prewarm joins and Skill discovery. See `docs/performance/v050-launch-connect-baseline.md` for a single-run baseline.

### Fixes

- Project Memory catalog requests now stay within the runtime limit.
- Skill enablement replays are idempotent.
- Errors are no longer swallowed by a follow-up refresh.
- Skills now load reliably around launch prewarm.
- Runtime library tests were brought back in line and are now gated in CI/release checks.

## Known limitations

- A ChatGPT session that holds the bootstrap token still has full permissions. Refusing management tools at the tunnel ingress is not a permission boundary, because shell tools are not sandboxed. A separate task, **tunnel token scoping**, is planned.
- Hidden `$` shares cannot be used as a Skill source, and a few local UNC aliases are not yet blocked.
- Windows is verified in CI only; there has been no physical-machine testing yet.
- Removing a Skill affects the whole local runtime, so every project loses it.
- `credential_push` may log an error at startup; this is under investigation.

## Validation

Source, helper, runtime-engine and Windows UI/portable suites ran in the integration branch; native Windows packaging and installed lifecycle remain CI evidence. The CI historical-upgrade gate now builds the public `v0.4.1` tag and upgrades it to the 0.5.0 candidate, and the synthetic installer-migration fixture now models `0.4.1 → 0.5.0`. Launch/connect numbers are a single warm-machine sample, not a benchmark suite.

## Distribution boundary

`.github/workflows/release.yml` remains the free macOS distribution path and does not publish the Windows candidate. Publishing Windows assets, enabling a Windows updater or changing the signing policy requires a separate explicit release decision.
