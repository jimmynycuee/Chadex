# Chadex 0.3.3

Chadex 0.3.3 closes two user-facing gaps in the ChatGPT ↔ Chadex workflow: ChatGPT host attachments can cross the explicitly trusted local file-import bridge, and update availability is discovered automatically so the blue **Update** action can appear next to Settings without a manual check first. This tag also carries the Windows W1-W5 source work that followed v0.3.2.

## Changes

- Chadex Desktop now adds `WEBCODEX_MCP_TRUST_LOOPBACK_API_TOKEN_FILE_IMPORT=true` to its managed local Server env file when the key is absent. The runtime only honors this exception for a loopback-bound Server authenticated with a normal user API token, which matches the OpenAI Secure Tunnel topology used by Chadex. Non-loopback binds and other untrusted caller paths remain fail-closed.
- Existing explicit values are preserved. A user/operator who sets the file-import trust key to `false` is not overridden by Desktop startup.
- Automatic update discovery now performs one check shortly after each fresh app launch, regardless of a previous-process six-hour timestamp. A check completed after launch scheduling is reused to avoid duplicate requests.
- While the app remains installed/running, returning to Chadex after the existing six-hour interval triggers another automatic check. Manual **Check for Updates…** remains immediate.
- Automatic discovery is intentionally quiet: when a release is found it populates the existing `availableRelease` state, causing the blue **Update** button beside Settings to appear, but it does not steal focus with the manual-check alert.
- Windows product metadata is synchronized to 0.3.3, and the W5 synthetic upgrade fixture now exercises 0.3.2 → 0.3.3. Windows runtime, desktop, source-integrity, installer, lifecycle, and upgrade work is present in the release tree.

The main-branch CI repeats the native Windows gates; the tag release workflow independently repeats public-history, source-release, and macOS package gates before publishing.

## Distribution boundaries

The public `Free Release` workflow for v0.3.3 publishes the macOS 14+ Apple Silicon DMG and SHA-256 sidecar. It uses Hardened Runtime with ad-hoc signing and is not notarized; first launch may require **System Settings → Privacy & Security → Open Anyway**.

Windows W5 runs in CI and produces an unsigned installer candidate for validation, but `.github/workflows/release.yml` does not publish that Windows candidate as a public v0.3.3 release asset. Windows should therefore not be described as a signed/public binary release from this tag.

The file-import exception is intentionally local-topology-specific. It is not a general authorization bypass and must not be enabled as a substitute for proper OAuth/client trust on a network-accessible Server.
